# Multi-Agent LLM Architecture for BFIS

## Overview

This document describes a multi-agent LLM architecture for BFIS consisting of three specialized agents:

- **Commander LLM**: Orchestrates the other two agents, makes final decisions
- **Writer LLM**: Translates decisions into concrete commands (maps to BFIS actions)
- **Intel LLM**: Monitors battlefield state, provides structured updates from decoder snapshots

This is a clever MVP approach that aligns well with BFIS's existing component structure.

## How This Maps to BFIS

The BFIS architecture already has separation of concerns that matches this vision:

- **Intel Agent** = Snapshot Summarizer + Change Detector
  - Consumes `BfisContextSnapshot` from decoders
  - Generates tactical summaries (unit counts, positions, threats) (see `BFIS-Architecture.md:18-21`)
  - Detects changes between snapshots

- **Commander Agent** = Decider
  - Takes Intel's summaries and determines goals (see `decider.ts:16-19`)
  - Decides what actions to take

- **Writer Agent** = Command Adapter
  - Translates `BfisDecision` actions into Olympus commands (see `BFIS-service-definition.md:23`)
  - Maps action types (SPAWN, MOVE, ATTACK) to concrete API calls (see `bfis_olympus_integration_strategy.md:331-338`)

## File Structure and Module Organization

The multi-agent architecture follows BFIS's existing module organization pattern. All agent code lives under `bfis-service/src/agents/`:

> **Non‑Goals (MVP)**
> - Do not change Olympus core code (`backend/**`, `frontend/**`, `mod/**`).
> - Do not duplicate Olympus mission‑state logic (for example hostility detection); BFIS consumes results only.
> - Do not introduce persistent state stores, message queues, or WebSockets; MVP uses in‑process polling only.
> - Do not execute real Olympus commands in early MVP; Writer may log mapped commands instead of calling production endpoints.

```
bfis-service/src/agents/
├── intel-agent.ts          # Intel agent implementation with snapshot tools
├── commander-agent.ts      # Commander agent decision logic
├── writer-agent.ts         # Writer agent command translation
├── orchestrator.ts         # LangGraph state machine orchestrator
├── types.ts                # Agent-specific type definitions
└── tools/
    ├── snapshot-tools.ts   # Intel agent tools (get_current_snapshot, etc.)
    └── index.ts            # Tool exports
```

This structure mirrors existing BFIS patterns:
- `bfis-service/src/snapshot/` - Snapshot ingestion (spec-001)
- `bfis-service/src/context/` - Context normalization (spec-002)
- `bfis-service/src/decider/` - Decision logic (placeholder)

Each agent module exports a single class or factory function that implements the agent's core behavior. The orchestrator (`orchestrator.ts`) wires the agents together using LangGraph and manages the state machine.

`bfis-service/src/agents/types.ts` is the **single source of truth** for agent‑specific types (for example `TacticalSummary`, `SnapshotDelta`, `AgentState`). Code examples in this document mirror those interfaces but the implementation in `types.ts` governs.

## Type Definitions and Interfaces

Agent communication uses TypeScript interfaces defined in `bfis-service/src/agents/types.ts`. These types ensure type safety when passing data between agents:

```typescript
import type { BfisContextSnapshot } from "../context/types.js";
import type { BfisDecision, OlympusCoalition } from "../../../shared-schemas/index.js";

/**
 * Tactical summary generated by Intel agent from battlefield snapshot.
 * Provides high-level overview of unit counts, positions, and threats.
 */
export interface TacticalSummary {
  /** Unit counts by coalition */
  unitCounts: Record<OlympusCoalition, number>;
  /** Unit counts by category (Aircraft, GroundUnit, etc.) */
  categoryCounts: Record<string, number>;
  /** Key positions (airbases, bullseyes, unit clusters) */
  keyPositions: Array<{
    type: "airbase" | "bullseye" | "cluster";
    coalition?: OlympusCoalition;
    position: { lat: number; lon: number; altMeters?: number };
    label?: string;
  }>;
  /** Threat assessment (simplified for MVP) */
  threats: Array<{
    coalition: OlympusCoalition;
    description: string;
    severity: "low" | "medium" | "high";
  }>;
  /** Timestamp of snapshot this summary is based on */
  snapshotTime: string;
  /** Snapshot ID for traceability */
  snapshotId: string;
}

/**
 * Delta between two snapshots, detecting changes in battlefield state.
 */
export interface SnapshotDelta {
  /** New units that appeared since last snapshot */
  newUnits: Array<{ unitId: string; coalition: OlympusCoalition; category: string }>;
  /** Units that disappeared (destroyed or despawned) */
  destroyedUnits: Array<{ unitId: string; coalition: OlympusCoalition }>;
  /** Units with significant position changes */
  movedUnits: Array<{ unitId: string; oldPosition: { lat: number; lon: number }; newPosition: { lat: number; lon: number } }>;
  /** Changes in hostility status */
  hostilityChanged: boolean;
  /** Timestamp of previous snapshot */
  previousSnapshotTime: string;
  /** Timestamp of current snapshot */
  currentSnapshotTime: string;
}

/**
 * Mission context wrapper providing metadata for decision-making.
 */
export interface MissionContext {
  missionId: string;
  serverId: string;
  sessionHash: string;
  time: string;
  /** Whether hostilities have started */
  hostilitiesStarted: boolean;
}

/**
 * Output from Intel agent, containing tactical summary and detected changes.
 */
export interface IntelAgentOutput {
  summary: TacticalSummary;
  changes?: SnapshotDelta;
  timestamp: string;
  /** Raw snapshot for reference (optional, may be omitted to save tokens) */
  rawSnapshot?: BfisContextSnapshot;
}

/**
 * Input to Commander agent, containing Intel output and previous decision context.
 */

  intelSummary: TacticalSummary;
  changes?: SnapshotDelta;
  missionContext: MissionContext;

  previousDecision?: BfisDecision;
  /** Player intent (for Copilot mode) */
  playerIntent?: string;
}

/**
 * Input to Writer agent, containing Commander's decision and command mapping context.
 */
export interface WriterAgentInput {
  decision: BfisDecision;
  /** Available command mappings (from bfis_action_command_mapping.md) */
  availableCommands: string[];
}
```

## Multi-Agent Framework Options

For orchestrating three LLMs talking to each other, consider the following frameworks:

### LangGraph (from LangChain)

**Why it fits:**

- Built specifically for multi-agent workflows with state management
- Agents can pass messages/context between each other
- Supports tool calling (Intel agent can call decoder snapshot tools)
- Handles conversation loops and decision cycles
- TypeScript support via LangChain.js (see `llm-client.ts:0-9`)

**Example flow:**

```
Intel Agent (with snapshot tools) → Commander Agent → Writer Agent → Execute  
         ↑                                  ↓                           ↓  
         └──────────────── feedback loop ───────────────────────────────┘  
```

### AutoGen (Microsoft)

**Why it fits:**

- Designed for multi-agent conversations
- Supports tool/function calling for Intel agent
- Agents can critique each other's outputs
- Has TypeScript bindings

### CrewAI

**Why it fits:**

- Role-based agent system (Commander, Writer, Intel roles)
- Built-in task delegation
- Supports tools and memory
- Python-first but has Node.js integrations

## Agent Communication Protocol

Agents communicate through a shared LangGraph state object. The state schema defines all data passed between agents:

```typescript
import type { StateGraph } from "@langchain/langgraph";
import type { IntelAgentOutput, CommanderAgentInput, WriterAgentInput, BfisContextSnapshot, BfisDecision } from "./types.js";

/**
 * LangGraph state schema for multi-agent orchestration.
 * All agents read from and write to this shared state object.
 */
export interface AgentState {
  /** Current battlefield snapshot (from SnapshotReader) */
  currentSnapshot: BfisContextSnapshot | null;
  /** Previous snapshot for change detection */
  previousSnapshot: BfisContextSnapshot | null;
  /** Intel agent output (tactical summary + changes) */
  intelOutput: IntelAgentOutput | null;
  /** Commander agent input (derived from intelOutput + context) */
  commanderInput: CommanderAgentInput | null;
  /** Commander agent decision */
  decision: BfisDecision | null;
  /** Writer agent input (derived from decision) */
  writerInput: WriterAgentInput | null;
  /** Command execution results */
  commandResults: Array<{ 
    commandHash: string; 
    status: "PENDING" | "SENT" | "CONFIRMED" | "FAILED"; 
    error?: string;
  }> | null;
  /** Error state (if any agent fails) */
  error: { 
    agent: "intel" | "commander" | "writer" | "orchestrator"; 
    message: string;
    timestamp: string;
    recoverable: boolean;
  } | null;
  /** Human approval state for Copilot / human-in-the-loop */
  userApproval?: boolean | null;
  /** Cycle metadata */
  cycleId: string;
  cycleStartTime: string;
  cycleEndTime: string | null;
}
```

**Message Passing Format:**

Agents pass data through the state object using LangGraph's state update pattern:
- Each agent node reads from `AgentState`
- Agent processes data and updates specific state fields
- Next agent in chain reads updated state
- State is immutable - agents create new state objects, not mutations

**State Persistence:**

For MVP, state is in-memory only. Future enhancements:
- Checkpoint state to disk for recovery
- Persist state across service restarts
- Enable state replay for debugging

**Error Propagation:**

Errors propagate through the state object:
- Agent sets `state.error = { agent: "intel", message: "...", timestamp, recoverable }`
- Orchestrator checks `state.error` after each node
- If error present, skip remaining nodes and log error
- Return partial results if available

## Intel Agent Tool Design

The Intel agent uses LangGraph tools to interact with the snapshot system. Tools are defined in `bfis-service/src/agents/tools/snapshot-tools.ts` and registered with the Intel agent's LLM.

### Tool 1: `get_current_snapshot`

**Signature:**
```typescript
async function get_current_snapshot(): Promise<BfisContextSnapshot>
```

**Implementation:**
- Calls `SnapshotReader.readContextOnce()` (see `snapshot-reader.ts:1254`)
- Returns complete `BfisContextSnapshot` with all context data
- Throws error if snapshot fetch fails (propagates to agent error handling)

**Error Handling:**
- HTTP errors: Log `bfis-snapshot-http-error` and throw
- Decode errors: Log `bfis-snapshot-decode-error` and throw
- Network timeouts: Retry once, then throw

**Tool Registration (LangGraph):**
```typescript
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const getCurrentSnapshotTool = tool(
  async () => {
    return await snapshotReader.readContextOnce();
  },
  {
    name: "get_current_snapshot",
    description: "Fetches the current battlefield snapshot from Olympus, including units, airbases, bullseyes, spots, drawings, logs, and weapons state.",
    schema: z.object({}), // No parameters
  }
);
```

### Tool 2: `get_snapshot_summary`

**Signature:**
```typescript
async function get_snapshot_summary(
  snapshot: BfisContextSnapshot
): Promise<TacticalSummary>
```

**Implementation:**
- Input: `BfisContextSnapshot` from Tool 1
- Uses Lodash to group/count units by coalition and category
- Uses Turf.js for spatial analysis:
  - Calculate unit clusters using `turf.clustersDbscan()`
  - Compute distances between key positions
  - Identify geographic concentrations
- Generates threat assessment based on unit counts and positions
- Returns `TacticalSummary` object

**Summary Structure:**
- `unitCounts`: Count by coalition (BLUE, RED, NEUTRAL, UNKNOWN)
- `categoryCounts`: Count by unit category (Aircraft, GroundUnit, etc.)
- `keyPositions`: Array of important locations (airbases, bullseyes, unit clusters)
- `threats`: Array of threat assessments with severity levels
- `snapshotTime` and `snapshotId`: For traceability

**Tool Registration:**
```typescript
const getSnapshotSummaryTool = tool(
  async ({ snapshot }: { snapshot: BfisContextSnapshot }) => {
    return await generateTacticalSummary(snapshot);
  },
  {
    name: "get_snapshot_summary",
    description: "Generates a tactical summary from a battlefield snapshot, including unit counts, key positions, and threat assessment.",
    schema: z.object({
      snapshot: z.any(), // BfisContextSnapshot type
    }),
  }
);
```

### Tool 3: `detect_changes`

**Signature:**
```typescript
async function detect_changes(
  currentSnapshot: BfisContextSnapshot,
  previousSnapshot: BfisContextSnapshot | null
): Promise<SnapshotDelta | null>
```

**Implementation:**
- Compares `currentSnapshot` with `previousSnapshot`
- Detects new units: Units in current but not in previous (by `unitId`)
- Detects destroyed units: Units in previous but not in current
- Detects moved units: Units with position changes > threshold (default 1000m)
- Detects hostility changes: Compares `hostility.hostilitiesStarted` flag
- Returns `SnapshotDelta` object or `null` if no previous snapshot

**Comparison Algorithm:**
1. Build unit ID sets from both snapshots
2. New units = current IDs - previous IDs
3. Destroyed units = previous IDs - current IDs
4. For common IDs, compare positions (Turf.js `turf.distance()`)
5. Compare hostility flags

**Caching:**
- Previous snapshot is cached in Intel agent state
- Cache cleared on `sessionHash` change
- Cache persists across agent cycles within same session

**Tool Registration:**
```typescript
const detectChangesTool = tool(
  async ({ currentSnapshot, previousSnapshot }: { 
    currentSnapshot: BfisContextSnapshot; 
    previousSnapshot: BfisContextSnapshot | null 
  }) => {
    if (!previousSnapshot) return null;
    return await compareSnapshots(currentSnapshot, previousSnapshot);
  },
  {
    name: "detect_changes",
    description: "Compares current snapshot with previous snapshot to detect new units, destroyed units, position changes, and hostility status changes.",
    schema: z.object({
      currentSnapshot: z.any(),
      previousSnapshot: z.any().nullable(),
    }),
  }
);
```

## Error Handling Strategy

Each agent has specific error handling behavior that propagates through the LangGraph state:

### Intel Agent Error Handling

**Tool Failures:**
- `get_current_snapshot()` failure:
  - Log `bfis-intel-snapshot-error` with error details
  - Set `state.error = { agent: "intel", message: "Snapshot fetch failed" }`
  - Return empty `IntelAgentOutput` with error flag (fallback behavior)
  - Orchestrator continues to Commander with empty intel (Commander handles gracefully)

- `get_snapshot_summary()` failure:
  - Log `bfis-intel-summary-error` with error details
  - Return partial summary if possible (unit counts only)
  - If complete failure, set error state

- `detect_changes()` failure:
  - Log `bfis-intel-changes-error` with error details
  - Return `null` for changes (non-fatal, Commander can proceed)
  - Previous snapshot cache cleared on error

**Retry Strategy:**
- Tool failures retry once with exponential backoff (1s delay)
- Network timeouts: Retry once
- Decode errors: No retry (data corruption)

### Commander Agent Error Handling

**LLM Failures:**
- LLM API failure (network, timeout):
  - Retry up to 2 times with exponential backoff (2s, 4s)
  - If all retries fail, fallback to rules-based decision (if `enableRulesFallback: true`)
  - Log `bfis-commander-llm-error` with retry count
  - Set `state.error = { agent: "commander", message: "LLM failed, using fallback" }`

- LLM response parsing failure (malformed JSON):
  - Log `bfis-commander-parse-error` with response snippet
  - Attempt to extract partial decision from response
  - If extraction fails, fallback to rules-based decision
  - Set error state (non-fatal, Writer can handle empty decision)

**Decision Validation:**
- Validate `BfisDecision` structure before proceeding
- Check action count against `maxActionsPerDecision`
- Validate action types against allowed set
- Invalid decision: Log error, fallback to rules-based

**Rules-Based Fallback (High-Level):**
- Fallback decisions must be deterministic and conservative, prioritizing defensive behavior and human expectations:
  - Do not spawn new units before `hostilitiesStarted === true` (respecting Olympus hostility logic as the source of truth).
  - Prefer actions that defend BLUE key assets (for example airbases and critical infrastructure) over aggressive deep strikes.
  - Enforce `maxActionsPerDecision` strictly and avoid issuing conflicting actions to the same unit or area.
  - When in doubt or on repeated failures, emit a **no‑op** decision with clear reasoning in logs instead of guessing.
- Fallback logic is implemented in Commander as a separate rules module so it can be unit‑tested independently of LLM behavior.

### Writer Agent Error Handling

**Command Mapping Failures:**
- Unknown action type:
  - Log `bfis-writer-unknown-action` with action type
  - Skip action, continue with remaining actions
  - Set partial error in state (non-fatal)

- Command parameter validation failure:
  - Log `bfis-writer-validation-error` with action and error
  - Skip action, continue with remaining actions
  - Return partial command results

**Command Execution Failures:**
- HTTP errors from Olympus:
  - Log `bfis-writer-command-error` with command hash and status
  - Mark command as failed in `commandResults`
  - Continue with remaining commands (partial execution)

- Command timeout:
  - Log `bfis-writer-command-timeout` with command hash
  - Mark command as failed
  - Continue with remaining commands

### Error Propagation Through State

**State Error Field:**
```typescript
// AgentState.error structure
state.error = {
  agent: "intel" | "commander" | "writer" | "orchestrator",
  message: string,
  timestamp: string,
  recoverable: boolean // true if other agents can continue
}
```

**Orchestrator Error Handling:**
- After each agent node, check `state.error`
- If `error.recoverable === true`, continue to next agent
- If `error.recoverable === false`, abort cycle and log error
- Log `bfis-orchestrator-cycle-error` with full error context
- Return partial results if available

**Error Recovery:**
- Intel errors: Commander proceeds with empty intel (may produce limited decision)
- Commander errors: Writer proceeds with empty decision (no commands executed)
- Writer errors: Partial command execution, results logged

## State Management Details

The LangGraph state object (`AgentState`) is the single source of truth for agent communication. State management follows immutable update patterns:

### State Object Structure

**Complete State Schema:**
```typescript
export interface AgentState {
  // Snapshot data
  currentSnapshot: BfisContextSnapshot | null;
  previousSnapshot: BfisContextSnapshot | null;
  
  // Agent outputs
  intelOutput: IntelAgentOutput | null;
  commanderInput: CommanderAgentInput | null;
  decision: BfisDecision | null;
  writerInput: WriterAgentInput | null;
  
  // Execution results
  commandResults: Array<{
    commandHash: string;
    status: "PENDING" | "SENT" | "CONFIRMED" | "FAILED";
    error?: string;
  }> | null;
  
  // Error state
  error: {
    agent: string;
    message: string;
    timestamp: string;
    recoverable: boolean;
  } | null;
  
  // Cycle metadata
  cycleId: string; // UUID for this cycle
  cycleStartTime: string; // ISO timestamp
  cycleEndTime: string | null; // ISO timestamp when cycle completes
}
```

### State Flow Through Agents

**Data Flow Pattern:**
1. **Orchestrator initializes state:**
   - Sets `currentSnapshot` from SnapshotReader
   - Sets `previousSnapshot` from cache (if available)
   - Generates `cycleId` (UUID)
   - Sets `cycleStartTime`

2. **Intel agent updates state:**
   - Reads `currentSnapshot` and `previousSnapshot`
   - Generates `intelOutput` (summary + changes)
   - Updates state: `state.intelOutput = intelOutput`
   - Caches `currentSnapshot` as `previousSnapshot` for next cycle

3. **Commander agent updates state:**
   - Reads `intelOutput` and `missionContext` (from `currentSnapshot.base`)
   - Generates `commanderInput` from intel
   - Produces `decision`
   - Updates state: `state.decision = decision`

4. **Writer agent updates state:**
   - Reads `decision`
   - Generates `writerInput` (command mappings)
   - Executes commands, collects `commandResults`
   - Updates state: `state.commandResults = commandResults`

5. **Orchestrator finalizes state:**
   - Sets `cycleEndTime`
   - Logs cycle completion
   - Returns final state

### Previous Snapshot Caching

**Cache Management:**
- The orchestrator maintains the canonical `previousSnapshot` value in `AgentState`. This is the snapshot that Intel sees on the **next** cycle for change detection.
- Implementations **may** also keep an internal Intel‑agent cache (for example for summary caching), but that cache is a performance optimization only and must be derived from and consistent with the `AgentState.previousSnapshot`.
- Cache key for internal Intel caches SHOULD be `sessionHash` to ensure cache is cleared on mission reset.
- Any internal caches MUST be cleared when:
  - `sessionHash` changes (mission reset), or
  - Cache size exceeds limit (for example FIFO eviction, max 10 snapshots).

### State Checkpointing (Future)

**Checkpoint Requirements:**
- Save state to disk after each agent node (optional, configurable)
- Checkpoint format: JSON serialization of `AgentState`
- Checkpoint location: `bfis-service/logs/checkpoints/`
- Checkpoint naming: `checkpoint-{cycleId}-{nodeName}.json`

**Recovery:**
- Load latest checkpoint on service restart
- Resume cycle from checkpoint (future enhancement)
- Checkpoint cleanup: Keep last N checkpoints, delete older

### State Cleanup on Session Hash Changes

**Session Reset Handling:**
- Detect `sessionHash` change in `currentSnapshot`
- Clear all state caches:
  - Previous snapshot cache
  - Intel agent cache
  - Any other agent-specific caches
- Reset state to initial values:
  - `previousSnapshot = null`
  - `intelOutput = null` (if in progress)
  - Clear error state
- Log `bfis-orchestrator-session-reset` event

## LangGraph Implementation Details

The orchestrator (`bfis-service/src/agents/orchestrator.ts`) uses LangGraph to define the multi-agent workflow as a state machine.

### Graph Structure

**Nodes:**
1. **`intelNode`** - Intel agent processes snapshot
2. **`commanderNode`** - Commander agent makes decision
3. **`writerNode`** - Writer agent maps commands
4. **`checkErrorNode`** - Error checking after each agent

**Edges:**
- `START → intelNode`
- `intelNode → checkErrorNode`
- `checkErrorNode → commanderNode` (if no error) OR `END` (if fatal error)
- `commanderNode → checkErrorNode`
- `checkErrorNode → writerNode` (if no error) OR `END` (if fatal error)
- `writerNode → checkErrorNode`
- `checkErrorNode → END`

**Graph Definition:**
```typescript
import { StateGraph, END } from "@langchain/langgraph";
import type { AgentState } from "./types.js";

const workflow = new StateGraph<AgentState>({
  channels: {
    // Define state channels (matches AgentState interface)
    currentSnapshot: null,
    previousSnapshot: null,
    intelOutput: null,
    commanderInput: null,
    decision: null,
    writerInput: null,
    commandResults: null,
    error: null,
    cycleId: "",
    cycleStartTime: "",
    cycleEndTime: null,
  },
});

// Add nodes
workflow.addNode("intel", intelNode);
workflow.addNode("commander", commanderNode);
workflow.addNode("writer", writerNode);
workflow.addNode("checkError", checkErrorNode);

// Add edges
workflow.setEntryPoint("intel");
workflow.addEdge("intel", "checkError");
workflow.addConditionalEdges("checkError", routeAfterError);
workflow.addEdge("commander", "checkError");
workflow.addEdge("writer", "checkError");
workflow.addEdge("checkError", END);
```

```typescript
async function checkErrorNode(state: AgentState): Promise<Partial<AgentState>> {
  if (state.error && !state.error.recoverable) {
    // Fatal error - abort cycle
    return { cycleEndTime: new Date().toISOString() };
  }
  // Recoverable error or no error - continue
  return {};
}
```

### Conditional Routing Logic

**Route After Error:**
```typescript
function routeAfterError(state: AgentState): string {
  if (state.error) {
    if (state.error.agent === "intel" && state.error.recoverable) {
      return "commander"; // Continue with empty intel
    }
    if (state.error.agent === "commander" && state.error.recoverable) {
      return "writer"; // Continue with empty decision
    }
    return END; // Fatal error
  }
  
  // No error - route to next agent
  if (!state.intelOutput) return "commander";
  if (!state.decision) return "writer";
  return END; // Cycle complete
}
```

## Performance Targets

Performance targets ensure the multi-agent system meets real-time decision-making requirements.

### Latency Targets

**End-to-End Latency:**
- Target: < 5 seconds from snapshot fetch to command execution
- Breakdown:
  - Snapshot fetch: < 1 second (from SnapshotReader)
  - Intel agent processing: < 1 second (summary generation)
  - Commander agent processing: < 2 seconds (LLM decision)
  - Writer agent processing: < 1 second (command mapping)
  - Total: < 5 seconds

**Measurement:**
- Log cycle duration in `bfis-orchestrator-cycle-completed` event
- Track `cycleDurationMs` field
- Alert if cycle exceeds 5 seconds

### Token Budgets

**Per-Agent Token Limits:**

**Intel Agent:**
- Input tokens: ~2000 (snapshot summary, previous summary)
- Output tokens: ~500 (tactical summary JSON)
- Total: ~2500 tokens per cycle
- Max tokens config: `AgentConfig.intel.maxTokens` (default: 2000)

**Commander Agent:**
- Input tokens: ~3000 (intel summary, mission context, previous decision)
- Output tokens: ~1000 (decision JSON with reasoning)
- Total: ~4000 tokens per cycle
- Max tokens config: `AgentConfig.commander.maxTokens` (default: 4000)

**Writer Agent:**
- Input tokens: ~1500 (decision, command mapping reference)
- Output tokens: ~500 (command mappings)
- Total: ~2000 tokens per cycle
- Max tokens config: `AgentConfig.writer.maxTokens` (default: 2000)

**Total Cycle Token Budget:**
- Maximum: ~8500 tokens per cycle
- Average: ~6000 tokens per cycle (with caching)

### Caching Strategies

**Intel Summary Caching:**
- Cache tactical summaries for unchanged snapshots
- Cache key: `snapshotId` or snapshot hash
- Cache TTL: 5 seconds (matches polling interval)
- Reduces token usage when no changes detected

**Commander Decision Caching:**
- Cache decisions for similar intel summaries (future optimization)
- Not implemented in MVP (always calls LLM)

**Optimization Notes:**
- Large snapshots (> 1000 units): Consider unit filtering before LLM
- Token limits: Truncate summaries if exceeding limits
- Batch processing: Process multiple decisions in single LLM call (future)

### Optimization for Large Snapshots

**Unit Filtering:**
- If snapshot has > 1000 units, filter to relevant subset:
  - Units within 100km of key positions
  - Units by coalition (focus on BLUE/RED, ignore NEUTRAL)
  - Units by category (prioritize Aircraft, GroundUnit)

**Summary Compression:**
- Use spatial clustering to reduce position data
- Aggregate unit counts by region instead of individual positions
- Truncate threat list to top N threats

**LLM Prompt Optimization:**
- Use structured JSON instead of natural language (fewer tokens)
- Remove redundant fields from prompts
- Use abbreviations for common terms
